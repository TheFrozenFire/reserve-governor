# Trust-axiom audit

**Date:** 2026-05-31
**Vantage:** trust-axiom auditor (adversarial review of the Reserve
Governor equivalence corpus).
**Baseline:** HEAD = `dbf4844 fv(R052): upstream MapToArray landing +
smoke test + audit refresh (task #265)`, build green
(`OPAM_SWITCH=rocq820 bash formal-verification/scripts/rocq-build`).
Findings carry over to subsequent doc-only commits up to `efc4e20`
(notes additions only; no equivalence file changes).

This is an exhaustive read-only audit. No equivalence file or
`Audit.v` or `WISDOM.md` was modified. Findings were generated by
running `Print Assumptions` against every milestone Qed theorem in
`proofs/equivalence/*.v` (52 milestones across 17 files), then
cross-referencing each unique trust axiom against its declaration
site and the proof that consumes it.

## Methodology

1. Enumerated every `^\s*Theorem ` in `proofs/equivalence/*.v` and
   filtered to milestone-shape names
   (`run_*_equivalent*`, `run_*_make_state`,
   `mutators_preserve_valid_chain`, three `reentrancy_*`).
2. Wrote a tiny `_check_assumptions_*.v` dispatcher placed inside
   `formal-verification/rocq/` (so the `-R . ReserveGovernor` binding
   reached it) that `Require`s each equivalence module and runs
   `Print Assumptions <Qualified.Name>` for every milestone. Output
   captured to `/tmp/assumptions_output.txt`, parsed to
   `/tmp/axioms_per_theorem.json`.
3. For each axiom that surfaced, read its declaration site and any
   companion sanity lemma (`*_refl`, `*_trans`, characterization
   lemma, or downstream proof that consumes it).

## CRITICAL findings

### CRIT-1: `run_fun_cancel_238_at_proj_sim_admin` admits any `proposalId`

**Location:** `proofs/equivalence/Guardian.v:10209`.

**Assertion:**
```
forall codes env state_base sim memory governor
       targets_offset targets_length values_offset values_length
       calldatas_offset calldatas_length descriptionHash
       (proposalId : U256.t),     (* <— universally quantified  *)
  preconditions ->
  exists memory',
  {{? codes, env, ... | fun_cancel_238 ... ⇓ Result.Ok proposalId
   | Some (make_state env state_base memory' (proj_sim sim)) ?}}.
```

**Failure mode:** `proposalId` is universally quantified across the
Hoare triple's *output* slot. The actual walker is deterministic
(`fun_cancel_238` is a deterministic Yul function under `RunO`
semantics), so it returns exactly one `proposalId` for any given
input. The axiom as written asserts non-determinism in the output —
i.e., for **every** `proposalId` value, the walker has a run that
yields that value. This is provably false against the walker's
deterministic semantics: any single concrete run yields one
`proposalId`, not all of them. The axiom is therefore an
inconsistent statement; under any model where the walker is
non-vacuous (i.e., terminates on the success branch), it admits
False.

In practice the milestone (`run_cancel_equivalent_make_state`,
Guardian.v:10320) specializes `proposalId := getProposalId_oracle key`,
which is the intended value — but a future consumer can specialize
`proposalId` to literally anything and use the axiom to construct a
proof that the contract returned that arbitrary value.

**Sanity check elsewhere:** none. The companion `igovernor_*` axioms
(Guardian.v:10137-10175) all have `True` conclusions and so don't
constrain `proposalId` either.

**Recommended action:**
1. Change the axiom statement to take `proposalId` as a function of
   the sim oracle: drop the universal quantifier, replace the output
   with `Result.Ok (getProposalId_oracle key)` (or pass the oracle as
   a Variable). The axiom would then assert "the walker returns *the*
   oracle's proposalId" rather than "for every proposalId, the walker
   returns that proposalId."
2. Add a sanity Lemma upstream of the milestone:
   `walker_proposalId_unique : forall p1 p2, ... -> Result.Ok p1 = Result.Ok p2`,
   which is impossible to discharge against the axiom as written —
   that impossibility is itself the proof that the current shape is
   unsound.
3. Apply the same fix to `run_fun_cancel_238_at_proj_sim_guardian`
   (Guardian.v:10266).

### CRIT-2: `run_fun_getRoleMembers_672_at_proj_sim` post-condition is `∃ memPtr ∃ state'`

**Location:** `proofs/equivalence/AccessControlEnumerable.v:731`.

**Assertion:**
```
exists (memPtr : U256.t) (state' : RocqOfSolidity.State.t),
  {{? codes, env, Some state | fun_getRoleMembers_672 role ⇓ Result.Ok memPtr
   | Some state' ?}}.
```

The text comment at AccessControlEnumerable.v:723 claims "No buggy
walker can satisfy the axiom's post-condition: any walker that
skipped, duplicated, or misordered elements would produce a memory
image that disagrees with `body_map` at some `(role, i)`, failing
the existential." **This claim is false.** The post-condition is
just `Result.Ok memPtr` with `memPtr` existentially quantified —
it doesn't reference `body_map` at all. A walker that returns `0`
and corrupts no memory at all satisfies the axiom trivially with
`memPtr := 0` and `state' := state`.

**Failure mode:** the axiom asserts the existence of a memPtr and
state', which can be witnessed by anything. The milestone Qed for
`run_fun_getRoleMember_641_equivalent` (which is currently Qed)
consumes this axiom and a sibling concrete sload axiom; the
sibling carries the actual content. So in *practice* the milestone
pulls its content from elsewhere, but the trust budget paid by
listing this axiom in `Print Assumptions` is misleading — the audit
reader cannot tell that this axiom is vacuous.

Note: `run_fun_getRoleMembers_672_at_proj_sim` appears in `Print
Assumptions` of `run_fun_getRoleMember_641_equivalent` (the
single-index getter) because the proof script calls into it
defensively. The single-index getter milestone does not actually
depend on the multi-element walker's memory contents.

**Sanity check elsewhere:** the single-element companion at
AccessControlEnumerable.v:433 (`run_fun__at_1791_at_proj_sim`) is
substantive — it binds `Result.Ok expected` where `expected` is
`StorableValue.map_get_u256 (role_values_body_map sim) (role, idx)`.

**Recommended action:**
1. Restate `run_fun_getRoleMembers_672_at_proj_sim`'s post-condition
   to characterize the memory image: at the returned `memPtr`, the
   first 32-byte word is the array length, and the next `length`
   words match `body_map sim (role, i)` for `i = 0..length-1`.
2. Until restated, remove the misleading claim at line 723.
3. Either remove the dependency from the single-index getter's
   proof (clean) or replace with the substantive `run_fun__at_1791_at_proj_sim`.

SimulatedStorage.t (membership in the appropriate keccak-derived
slot). The walker axioms then become substantive equations.

### MED-5: `MakeStateForm.keccak256_tuple2_offset_bound` (ThrottleLib) is the only meta-trust outside Guardian

**Location:** `proofs/equivalence/ThrottleLib.v` inside
`MakeStateForm` module.

**Assertion:**
```
Axiom keccak256_tuple2_offset_bound :
  forall key index offset, 0 <= offset < 32 ->
    0 <= keccak256_tuple2 key index /\
    keccak256_tuple2 key index + offset < 2 ^ 256.
```

This is a duplicate of Guardian.v:61's
`keccak256_tuple2_offset_bound`. Both axiomatize the same fact (the
hash is in `[0, 2^256)` and adding ≤31 doesn't overflow). The
"meta-trust" is that keccak256 produces values uniformly in U256
— a standard cryptographic axiom — but having two copies under
different namespaces (`MakeStateForm` vs `GuardianEquivalence`)
means the audit has to verify both.

**Recommended action:** lift one canonical version into
`RocqOfSolidity.proofs.RocqOfSolidity` (alongside the existing
`keccak256_tuple2` Parameter) as the framework-level trust
witness. The two consumers then `Import` the same axiom.

### MED-7: `StakingVaultRewards.proj_sim_concrete` is an unconstrained Parameter

### MED-11: `Storage.run_sstore_struct_field` framework primitive uses match-on-list-nth shape

**Location:** upstream `RocqOfSolidity.Storage.run_sstore_struct_field`
(surfaces in 11 milestones).

The axiom is conditional on `match List.nth_error values index with
| Some (MapStruct map) => ... | _ => True`. The `True` branch is
the worry: if `index` is out of bounds or the slot has a different
StorableValue variant, the axiom collapses to `True` and the proof
trivially holds. The proof-side discipline is to ensure the
preconditions match the actual storage layout; an audit needs to
verify each consumer doesn't accidentally fall into the `True`
branch.

**Recommended action:** if/when the framework is rebuilt, refactor
to fail-loud (`match ... | _ => False`) so misuse surfaces as a
proof failure rather than a vacuous discharge.

### MED-12: `RocqOfSolidity.Address.implies_and_mask` framework axiom

This is a framework-level axiom that asserts validity ⇒ mask.
It's load-bearing for three milestones. The axiom is standard
(bit-masking identity for in-range addresses) but it's a hidden
trust witness. Recommended to **Lemma**-ize once a 160-bit
verified BitMaskLib lands upstream.
